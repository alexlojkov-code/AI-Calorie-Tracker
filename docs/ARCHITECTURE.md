# Архитектура

```text
React + TypeScript (web)
  ├── Supabase Auth + PostgREST ── PostgreSQL с RLS
  └── Supabase Edge Functions
       ├── food-search ── USDA FoodData Central
       ├── add-food ── USDA → RPC атомарной записи в дневник
       ├── parse-meal ── OpenAI Responses API
       └── food-analysis ── OpenAI Responses API (vision)
       └── confirm-analysis ── USDA перепроверка → пакетная RPC запись
```

- Клиент содержит только Supabase URL и publishable key. Любые сторонние API-ключи хранятся в секретах Edge Functions.
- RLS проверяет владельца профиля, целей, дневника, рецептов и анализов. Позиция дневника получает доступ через принадлежащий пользователю приём пищи.
- Пищевая ценность сохраняется как снимок источника на момент добавления; расчёт порции выполняется детерминированно: значение на 100 г × масса / 100.
- `NULL` остаётся неизвестным и не подменяется нулём. Пустые поля ручного ввода также остаются `NULL`.
- Фото и текст возвращают редактируемый черновик. Он не сохраняется в дневник автоматически. Перед подтверждением каждый компонент нужно сопоставить с продуктом USDA и проверить массу. Сервер заново получает нутриенты и сохраняет пакет одной закрытой RPC-транзакцией; ручные значения пользователя проходят отдельно через RLS и явно помечаются.
- Для офлайн-режима кешируются только собранные статические файлы. Приватные ответы API и пользовательские данные Service Worker не кеширует.

## Ограничения первого вертикального среза

Каталог USDA не кешируется в таблице `foods`, а сохраняется в снимке дневника с FDC ID и исходными nutrient values. Rate limiting по аккаунту, Storage-политика фото, удаление аккаунта и ИИ-консультант ещё предстоит добавить.
